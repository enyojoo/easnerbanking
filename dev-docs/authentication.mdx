Every `v1` call uses a secret key.

Mint keys in Console: Settings → API keys. The list is the **current** Test or Live mode from the header. Create as many as you need.

```bash
export EASNER_SECRET_KEY=easner_sk_test_…
```

```bash
curl https://api.easner.com/v1/accounts \
  -H "Authorization: Bearer easner_sk_test_…"
```

`Bearer` is required. A bare key is also accepted. Missing or unknown keys return `401`.

Secret keys stay on the server. Publishable keys (`easner_pk_…`) are for the browser, Checkout only.

New keys can include Banking scopes (`accounts.read`, `accounts.write`, `transfers.write`) and Checkout. Restricted keys use a subset of those scopes. Existing checkout-only keys stay checkout-only until you mint a new key.

## Livemode

Livemode comes from the key prefix, not from a body field.

| Prefix | Mode |
|---|---|
| `easner_sk_test_` | Test |
| `easner_sk_live_` | Live |
| `easner_pk_test_` | Publishable, Checkout.js only |
| `easner_pk_live_` | Publishable, Checkout.js only |

A test key never sees live objects. A live key never sees test objects.

## Scopes

| Scope | Used for |
|---|---|
| `checkout` | `POST/GET /v1/checkout/sessions` |
| `accounts.read` | Customers, accounts, deposit instructions, deposit addresses, payment methods, destinations, transfers, transactions |
| `accounts.write` | `POST /v1/accounts`, `POST /v1/customers/:id/verification`, `POST /v1/accounts/:id/onramp_sessions` |
| `transfers.write` | Create customers, destinations, quotes, transfers |

A key without the required scope returns `403`:

```json
{
  "error": {
    "type": "permission",
    "code": "key_forbidden",
    "message": "This key cannot transfers.write"
  }
}
```

If a call returns `key_forbidden`, mint a new key from Settings → API keys with the missing scope.

## Idempotency

Send `Idempotency-Key` on writes that can move money. It is **only** honored on:

- `POST /v1/transfers` (create)
- `POST /v1/checkout/sessions`

Creating a customer, destination, quote, or onramp session twice creates two objects. Confirm uses the transfer `client_secret` (`easner_ta_…`), not `Idempotency-Key`. A merchant key on confirm returns `403` `customer_action_required`.

Use a new key per logical operation. Replays with the same key return the original transfer or session instead of sending twice. Keys longer than 256 characters are ignored.

```bash
curl https://api.easner.com/v1/transfers \
  -H "Authorization: Bearer $EASNER_SECRET_KEY" \
  -H "Content-Type: application/json" \
  -H "Idempotency-Key: $(uuidgen)" \
  -d '{"quote":"qt_…"}'
```

## Rate limits

`429` `{ "error": { "type": "rate_limit", "code": "rate_limit", "message": "Too many requests" } }` with `Retry-After: 60`.

Per IP, per minute: **120** reads, **30** writes. After the key authenticates, per business, per minute: **300** reads, **40** writes. Wait `Retry-After` seconds. Do not open a new send.

## Restrictions

If the business is restricted for send or deposit, the matching write returns `permission`.
