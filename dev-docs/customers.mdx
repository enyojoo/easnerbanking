A customer is your end user. They never log into Easner. You hold the id and call `v1`. Live send is authorized in your app (or the hosted review URL) with the transfer `client_secret`.

Creating a customer opens **their** vault and issues a USD `acct_` (USDC on Solana). Email and name are not enough for a live virtual account or onramp — start hosted verification first.

<Note>
  **Scope:** `GET` needs `accounts.read`. `POST` customer needs `transfers.write`. `POST` verification needs `accounts.write`.
</Note>

## Object

| Field | Type | Notes |
|---|---|---|
| `id` | string | `cus_…` |
| `email` | string \| null | Required to start live verification |
| `name` | string \| null | Used on bank details |
| `external_id` | string \| null | Your id. Use this to map your user |
| `easetag` | string \| null | In-network `@tag`. Allocated on create. Unique |
| `status` | string | `active` |
| `verification_status` | string | `unverified`, `pending`, `approved`, `rejected` |
| `livemode` | boolean | From the key |
| `created` | ISO-8601 | |

```json
{
  "id": "cus_…",
  "email": "ada@example.com",
  "name": "Ada",
  "external_id": "user_42",
  "easetag": "ada",
  "status": "active",
  "verification_status": "unverified",
  "livemode": false,
  "created": "2026-09-20T00:00:00.000Z"
}
```

`GET /v1/customers/:id` also includes `accounts` (issued balances for that customer).

## Create

```bash
curl https://api.easner.com/v1/customers \
  -H "Authorization: Bearer $EASNER_SECRET_KEY" \
  -H "Content-Type: application/json" \
  -d '{"email":"ada@example.com","name":"Ada","external_id":"user_42","easetag":"ada"}'
```

`201` on success. The response includes the issued USD account (the vault view) under `accounts`.

## List

`GET /v1/customers` → `{ "data": [ Customer, … ] }`

Newest first. Up to 100.

## Retrieve

`GET /v1/customers/:id` → Customer plus `accounts`.

`404` `not_found` if the id is missing or belongs to the other livemode.

## Start verification

```bash
curl https://api.easner.com/v1/customers/cus_…/verification \
  -H "Authorization: Bearer $EASNER_SECRET_KEY" \
  -H "Content-Type: application/json" \
  -d '{"return_url":"https://yoursite.com/verified"}'
```

```json
{ "status": "approved", "url": null }
```

| Mode | Result |
|---|---|
| Test | Sets `verification_status` to `approved`. `url` is `null` |
| Live | `{ "status": "pending", "url": "https://…" }` hosted form. Already-approved customers return `{ "status": "approved", "url": null }` |

Live create needs an email. `404` if the customer is missing.

A live `cus_` with only email and name cannot hold a named virtual account or card onramp until `approved`. The vault still exists; live bank details wait on verification.

## Events

| Event | When |
|---|---|
| `customer.created` | After a successful create |
| `customer.updated` | When the record changes, including `verification_status` |

## Expected

- Store `id`, `external_id`, and `easetag` on your side.
- Attach destinations with `"customer": "cus_…"`.
- Open EUR with `POST /v1/accounts` and `"customer": "cus_…"` — a second vault view, same customer.
- Start verification before live Receive.
