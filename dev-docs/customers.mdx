A customer is **your** end user. They never log into Easner — they onboard on **your** app. You store `cus_` and call `v1`. Creating one opens **their** vault and issues a USD `acct_` (USDC on Solana).

There are two verifications. Mixing them up is the usual onboarding bug.

| Who | What | Where |
|---|---|---|
| **You** (the business) | **KYB** — access to Easner | Banking → Settings → Verification. Not a `cus_`. Not Console. |
| **Your customer** (`cus_`) | **KYC** (person) or **KYB** (business) — onboard on your app so they can use a named vault and live Receive | `POST /v1/customers/:id/verification`. Console Customers → Verification. |

Email and name on create are not verification. Live bank details, chain addresses, and onramp wait until `verification_status` is `approved`.

<Note>
  **Scope:** `GET` needs `accounts.read`. `POST` customer needs `transfers.write`. `POST` verification needs `accounts.write`.
</Note>

## Onboard a customer

<Steps>
  <Step title="Create">
    `POST /v1/customers` with your `external_id`. Save `id` (`cus_…`) and the issued USD `accounts[0].id` (`acct_…`). In Console, create from Customers while Test is on.
  </Step>
  <Step title="Start verification">
    `POST /v1/customers/:id/verification` with a `return_url`. Test approves immediately (`url` is `null`). Live returns a hosted form — send that URL on your app so they complete KYC or KYB. Already-approved customers return `{ "status": "approved", "url": null }`.
  </Step>
  <Step title="Wait for approved">
    Poll `GET /v1/customers/:id` or handle `customer.updated`. Live Receive returns `403` `verification_required` until `approved`.
  </Step>
  <Step title="Publish Receive">
    After `approved`, fetch [bank details](/receive#virtual-account), a [wallet address](/receive#wallet-address), or a [card onramp](/receive#card-onramp).
  </Step>
</Steps>

Your KYB does not verify your customers. Completing Banking Settings does not set `verification_status` on a `cus_`.

## Object

| Field | Type | Notes |
|---|---|---|
| `id` | string | `cus_…` |
| `email` | string \| null | Required to start live verification |
| `name` | string \| null | Used on bank details |
| `external_id` | string \| null | Your id. Use this to map your user |
| `easetag` | string \| null | In-network `@tag`. Allocated on create. Unique |
| `status` | string | `active` |
| `verification_status` | string | `unverified`, `pending`, `approved`, `rejected` |
| `livemode` | boolean | From the key |
| `created` | ISO-8601 | |

```json
{
  "id": "cus_…",
  "email": "ada@example.com",
  "name": "Ada",
  "external_id": "user_42",
  "easetag": "ada",
  "status": "active",
  "verification_status": "unverified",
  "livemode": false,
  "created": "2026-09-20T00:00:00.000Z"
}
```

`GET /v1/customers/:id` also includes `accounts` (issued balances for that customer).

## Create

```bash
curl https://api.easner.com/v1/customers \
  -H "Authorization: Bearer $EASNER_SECRET_KEY" \
  -H "Content-Type: application/json" \
  -d '{"email":"ada@example.com","name":"Ada","external_id":"user_42","easetag":"ada"}'
```

`201` on success. The response includes the issued USD account (the vault view) under `accounts`.

## List

`GET /v1/customers` → `{ "data": [ Customer, … ] }`

Newest first. Up to 100. There is no next page. There is no customer `PATCH` — put `email` on create before live verification.

## Retrieve

`GET /v1/customers/:id` → Customer plus `accounts`.

`404` `not_found` if the id is missing or belongs to the other livemode.

## Start verification

```bash
curl https://api.easner.com/v1/customers/cus_…/verification \
  -H "Authorization: Bearer $EASNER_SECRET_KEY" \
  -H "Content-Type: application/json" \
  -d '{"return_url":"https://yoursite.com/verified"}'
```

```json
{ "status": "approved", "url": null }
```

| Mode | Result |
|---|---|
| Test | Sets `verification_status` to `approved`. `url` is `null`. No hosted form |
| Live | `{ "status": "pending", "url": "https://…" }` hosted KYC (person) or KYB (business). Already-approved customers return `{ "status": "approved", "url": null }` |

Live verification needs an email. `404` if the customer is missing.

A live `cus_` with only email and name cannot be issued a named virtual account or card onramp until `approved`. The vault still exists; live bank details wait on verification.

In Console, Customers → the `cus_` → Verification. Test approves in place. Live opens the hosted URL.

## Events

| Event | When |
|---|---|
| `customer.created` | After a successful create |
| `customer.updated` | When the record changes, including `verification_status` |

## Expected

- Store `id`, `external_id`, and `easetag` on your side.
- Attach destinations with `"customer": "cus_…"`.
- Open EUR with `POST /v1/accounts` and `"customer": "cus_…"` — a second vault view, same customer.
- Verify the `cus_` (KYC or KYB) before live Receive. KYB yourself in Banking for access to Easner.
- There is no customer update. Live verification needs `email` on create.
